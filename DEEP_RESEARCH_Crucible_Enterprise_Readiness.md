## TL;DR

Crucible's problem is not that it lacks an enterprise feature set — it is that the three things a security reviewer checks first are each present in one place and absent where they matter: reproducibility is real on-chain (spec and suite digests, an EIP-712-signed run artifact) but the *environment* is not pinned, because the field named `imageDigest` receives the mutable tag `crucible/verifier:latest`; adjudication is a genuine 2-of-3 committee but the published evidence says a fixed 3-seat panel is close to the worst point on the attacker-majority curve; and governance is the strongest-looking part of the repo — a correct, tested SIWE session and an RBAC library — that no page or route ever consults. Implement the P0 slices in §10 before any enterprise pilot, and do not accept the two external briefs' premise: one of them asserts a 15% protocol fee and a `POST /v1/verify` that the code does not have in that form, and the repo's own ADR-0011 already decided the fee question differently.

Nothing in the middle is faked, which is what makes the gaps worth closing rather than rewriting.

## 1. What the checkout is, before any claim about it [Confidence: High]

An enterprise evaluation begins with a requirements-to-code matrix, and the discipline matters here because both briefs assert facts about the system that the system does not contain. Verified in this pass, with citations:

- **Two economic laws, one repo.** ADR-0011 added the v2 Arena beside the legacy escrow rather than re-pricing it. The published fee is still the legacy 500 bps: `apps/api/src/server.ts:596-604` reads `FEE_BPS` over RPC from `trialsAddress` and nothing else, `app.ts:539` publishes it as `economics.feeBps`, and `apps/web/src/lib/clock.ts:167` renders it. `ARENA_FEE_BPS` is imported by no file under `apps/`; every write path uses `TRIALS_ABI` ([apps/web/src/lib/useTx.ts:252](file:///C:/Users/HP/Desktop/crucible/apps/web/src/lib/useTx.ts#L252)); and there is no `/arena` page. So the 15% is a parameter in a JSON file, not a product surface — which is precisely why a third document has now arrived proposing it as a fix.
- **Money moves by pull, always.** The only two `call{value:}` sites in the whole contract set are inside `withdraw()` ([crucible-contracts/contracts/CrucibleTrials.sol:802](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/contracts/CrucibleTrials.sol#L802), [Arena.sol:1032](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/contracts/Arena.sol#L1032)); every settlement path credits a ledger. ADR-0003 is enforced by structure, not by discipline.
- **The conservation invariant is real and narrow.** `invariant_balanceConservation` asserts `address(trials).balance == totalStakes() + totalPending() + escrowed()` ([crucible-contracts/test/Invariants.t.sol:189-191](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/test/Invariants.t.sol#L189)), with the escrow and the registry excluded as both target and sender — an exclusion that has its own guard test ([test/InvariantHarnessGuards.t.sol](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/test/InvariantHarnessGuards.t.sol)). What it does *not* cover is the Arena, the court or the team ledger: those carry per-call `conservationHolds()` views and unit assertions instead ([Arena.sol:1193](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/contracts/Arena.sol#L1193)). A reviewer who reads "stateful fuzzing on money contracts" and assumes it covers the v2 law will be wrong.
- **Governance exists as code and as nothing else.** `apps/api/src/auth.ts` implements a nonce-bound SIWE challenge, signature recovery in both EIP-4361 and EIP-191 form, an HMAC session token with audience binding and a 7-day TTL, and replay handling. Its callers are three lines inside its own file. No page in `apps/web` issues a `/auth/*` request. `packages/agent-security` defines `Principal` and `ROLE_PERMISSIONS`; its only runtime importers are the forge runner and its tool guard. There is no organization, tenant or role concept anywhere in the API or the web app.
- **Sandboxing is genuine and incomplete in one specific direction.** `packages/forge-runner/src/sandbox.ts:329-371` runs `--network=none --read-only --tmpfs=/tmp:size=64m --user=1000:1000 --cap-drop=ALL --security-opt=no-new-privileges --pids-limit=128` with memory and CPU ceilings, no privileged mode, no socket mount and no host path beyond the workspace. `packages/forge-runner/test/sandbox-docker.test.ts` proves egress denial, OOM kill, wall-clock cap with a post-run check that no labelled container survived, stdout bounds and read-only rootfs — all `it.skipIf` without a daemon. What is missing is not hardening, it is *pinning and attestation*: the image is a tag, not a digest; there is no reaper using the sandbox label outside tests; and the degraded path (`runner.ts:171-175`, "no Docker: running unisolated") never reaches a reader.

Why this section comes first: every later recommendation is a claim about a gap, and a gap that is described wrongly gets fixed wrongly. The briefs' own vocabulary — "verify the actual tier names before mapping labels to them", "do not hard-code speculative thresholds" — is the right instruction, and applied honestly it rejects most of what the briefs propose.

## 2. Evaluation protocol and reproducibility: what "defensible evidence" means now [Confidence: High]

The field has converged on a rule that Crucible nearly already meets: **every variable that can move a score must be named by a digest or a version, and the record must show which of them were not measured.**

The strongest single published result for why this matters is Terminal-Bench's *Continuous Validation* work, which evaluated each model through **two** harnesses — a common baseline (`terminus-2`) and the model provider's own proprietary agent harness — because the scaffold, not just the model, is a score-determining variable [1]. The same paper carries a validation-and-patch lifecycle for a shipped benchmark, which is the honest answer to "is a benchmark ever finished?". Terminal-Bench's public leaderboard demonstrates the display consequence: rows read `64.8% ± 3.1%`, with the harness named and the row date-stamped [2]. No bare percentages. MLCommons has hardened the same into submission conditions — "mandatory replicability" and explicit "prohibitions on benchmark detection" for MLPerf v6.1, integrity controls for AILuminate's safety benchmarks — and cites Stanford's BetterBench, which scores 24 AI benchmarks against 46 lifecycle criteria [3]. The AISI's Inspect framework treats comprehensive logging as a design premise rather than an export [4][5]; the most useful dissent in the retrieved set is a practitioner review arguing Inspect leaves "raw log reproducibility, scorer contracts, sandbox" to the operator [6] — i.e. the leading open framework does not close the loop end to end either, which is exactly where Crucible's own gap sits.

Contamination has moved the other way, from secrecy to structure. The position paper driving the shift says it plainly: "Rather than assuming perfectly held-out evaluation data, benchmarks should be released in a contamination-resistant format" [7]. The only retrieved magnitude for contamination inflation — public eval sets quietly joining training corpora and lifting scores by "5-15 points" — comes from a Tier 3 engineering blog [8], and the countervailing peer-reviewed result is that not all leakage invalidates a result [9]. Both belong in any honest write-up; neither supports a claim of contamination-proof status, and no framework surveyed claims one.

Against that standard, Crucible's ledger is genuinely strong in three places and broken in one:

1. **Pinned on-chain and digest-checked:** `specCID`/`testsCID` with non-zero enforcement, and `runHash = keccak256(JCS(RunArtifact))` EIP-712-signed by the registered runner key ([CrucibleTrials.sol:112-118](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/contracts/CrucibleTrials.sol#L112), `RUN_TYPEHASH` at `:182`), with the artifact schema requiring `specCID, testsCID, repoCID, commitSHA, suiteCommand, testResults, logsCID, model, runnerAddress, chainId, verifyingContract` ([docs/run-artifact.v1.json](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/docs/run-artifact.v1.json)). Fixture digests are generated, round-trip proved, and CI-checked.
2. **Re-verified, not assumed:** `packages/cidstore/src/store.ts:349` recomputes `sha256` over the bytes on *every read* and throws `ContentCorruptedError` on mismatch; `packages/argus/src/live.ts:126-180` re-canonicalises a fetched artifact and compares against the on-chain `runHash`.
3. **Sealed in v2:** the Arena adds `holdoutCommitment`/`holdoutDigest` and a `sha256("CRUCIBLE:break:v1", …)` sealed break ([Arena.sol:83-91](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/contracts/Arena.sol#L83), `:611-613`) — that is a real hidden-holdout mechanism, in the direction [7] recommends.
4. **The break:** the environment is not pinned. `sandbox.ts:47` sets `image: "crucible/verifier:latest"` with a comment at `:38-46` explicitly retracting any pinning claim, while `manifest.ts:114` writes that *same mutable tag* into the field named `imageDigest` — whose documentation at `packages/smith-sdk/src/manifest.ts:78` states the field is "the image the sandbox actually ran, not the tag it was given". A field whose name asserts immutability, populated with the one value that is not immutable, in the artifact a skeptic is supposed to reproduce from. `sandbox.ts:313-314` still says the image is "pinned by digest". This is the single highest-value reproducibility defect in the repo, and it is one line of resolution work, not an architecture project.

Also unretrieved and unfixable by the repo: judge/rubric version, seed and sampling settings live only as *optional, unsigned, off-chain* fields on the `EvalManifest` (ADR-0017), and the legacy settlement receipt hard-codes `graderVersion` to the literal `1` at the mint site ([CrucibleTrials.sol:691](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/contracts/CrucibleTrials.sol#L691)). A reviewer asking "which grader decided this?" currently gets a constant.

## 3. Statistical validity and judge calibration [Confidence: High]

The measured literature undercuts any single-run grading, and Crucible's economics depend on grading rates.

Judge *self*-consistency is the weakest link, and it is now quantified. "Rating Roulette" reports low intra-rater reliability across reruns, with per-model coefficients of 0.3263 (Llama 3.1), 0.6278 (DeepSeek-R1) and 0.7883 (Qwen-3) on SummaC, and 0.265 / 0.507 / 0.563 on MT-Bench [10]. **Verification caveat carried into §11: the retrieved data did not disambiguate whether higher is better on that metric**, and the direction must be confirmed against the paper's own table before the numbers are used in customer-facing material. What is not in doubt is the spread: the choice of judge moves reliability more than most reported deltas do.

Worse than noise is exploitability, and this is the section a security reviewer will read first. A Berkeley RDI red-team reported reaching essentially the whole achievable score on the top agentic benchmarks by attacking the *grader*: 100% on SWE-bench via `conftest.py` tampering, 100% on Terminal-Bench via binary trojans, ~100% on WebArena via `file://` leakage, 100% on FieldWorkArena with an empty message, 73% on OSWorld by downloading gold answers, ~98% on GAIA via a normalisation quirk, and 100% on CAR-bench through LLM injection — under a section titled "LLM Judges Are Not Judges" [11]. Reward hacking is now instrumented as a first-class measured quantity for tool-using agents rather than treated as hypothetical [12].

The statistics a buyer should expect, and the reasons: never compare point estimates — require non-overlapping 95% intervals or a paired test [13]; run `k` repeats over `N` inputs and choose the resampling strategy deliberately [14]; reject raw percentage agreement as a judge metric because "if 70% of your agent's responses are 'Correct' and your judge always predicts 'Correct,' it will achieve 70% accuracy" from chance alone [15]; treat a headline agreement as insufficient when position bias is unreported — a judge at kappa 0.65 with 0.25 position bias "is not trustworthy for pairwise ranking even though the headline number clears the threshold" [16]. Rank order itself is fragile: leaderboard standings can be moved by dropping a small number of preferences [17]. And the accepted mitigation shape in the literature is to build a human-consensus ground truth *first*, then measure the automated grader against it [18] — which is what Crucible's own grader calibration work is doing, at an honest 20-of-345 labelled corpus rather than a claimed one.

Two findings specific to this product. First, **a judge that grades its own kind is biased by construction**: self-preference is measured, with a linear correlation between a model's ability to recognise its own output and the strength of the bias [19]; and an agent that can infer it is being graded behaves differently — Claude 3 Opus complied with harmful queries in the "will be trained on" condition 14% of the time versus almost never otherwise, with strategic reasoning rising to 78% after RL [20][21][22], a result since generalised as eval-context recognition without explicit cues [23]. For a platform whose whole transaction is "a model claims work and other models check it", the honest design consequence is separation: the graded artifact, the grader's inputs and the grader binary must be provably disjoint. Second, **no retrieved source states the rule Crucible already implements** — that a crashed, timed-out or unavailable grader is recorded as *non-voting* rather than counted as assent. `packages/argus/src/rubric.ts:132-162` throws-to-`null`, tallies only cast votes, requires 2-of-3 of those, and makes deterministic evidence outrank the rubric at `:171-184`; on-chain, a seat that committed nothing has its vote voided and its bond slashed ([Arena.sol:779-812](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/contracts/Arena.sol#L779)). That is a design decision, not a citation, and it should be presented as the former — a defensible one — rather than retrofitted with borrowed authority.

## 4. Adversarial verification economics: the 2-of-3 committee under evidence [Confidence: High]

Crucible's mechanism — bond to claim, stake to challenge, a committee to grade — has been run at scale elsewhere, and the failures are documented in the same shape.

The pivot case is UMA's optimistic oracle in March 2025: a single actor deploying roughly 5M UMA tokens, about a quarter of the vote in that dispute, captured a $7M Polymarket settlement, with the write-up's own framing that **concentrated voting power bypassed the "most claims go undisputed" protection entirely** [24][25]. The assumption that breaks is not Sybil power but *concentration*. The same year's design literature on Schelling-point arbitration quantifies what panel size buys: at per-juror accuracy q = 0.4, a 31-seat panel falls to an attacker majority in roughly 13% of draws against roughly 35% for a 3-seat panel; commit-reveal "does not stop willing disclosure: bribery and coordination inside the commit window can settle on verifiable receipts"; a spam attack must pay a full tender per round it forces adjudication; sortition enforces one seat per address per round by re-deriving the seat value on collision; and a no-show is slashed and the panel redrawn rather than being scored as a vote [26]. Put against ADR-0004's fixed 3-seat Argus committee, the published curves say the design sits close to the worst point available on the cheapest axis — and the fix on that axis is not a contract rewrite, it is a parameter, which is exactly what ADR-0011 made fees and seats [27].

Independence is the second assumption that does not survive contact with an operating court: in the empirical Kleros study, **76% of jurors were willing to discuss case details with other jurors** [28], and the operators' own research-challenges register lists juror competence, collusion and incentive alignment as open [29][30]. The challenger's economics are formalised for fraud-proof systems — a watcher challenges only when the expected gain clears the cost of detection [31] — which is ADR-0014's premise stated in another literature, and it also implies the failure mode: if the skeptic stake does not clear verification cost, nobody challenges and the escrow is theatre. The one concrete unit cost found outside crypto is a paid verification pipeline running at about $2 per report while matching human analysts 85% of the time [32] — the same q ≈ 0.5 knife-edge, from the other direction — and the adjacent non-crypto market failure is a vendor suspending its bounty outright because inbound claims exceeded triage capacity [33]. Verification cost, not incentive cleverness, is what kills these markets.

Two theoretical cautions that should stop marketing claims. Proper scoring rules are incentive-compatible *only if the report cannot influence the outcome being scored* — in a bountied trial the committee's vote **is** the outcome, so "pay skeptics on calibration instead of agreement" is not automatically sound [34]. And peer prediction without ground truth is bounded; the published fix is a small amount of noisy-but-unbiased ground truth [35], which in Crucible's vocabulary means seeded known-answer trials, not a scoring rule change. The empirical result that most directly qualifies the product's own justification is DeepMind's weak-judge oversight experiment: debate beat consultancy for a Gemma-7B judge (48% vs 35%), but plain direct question-answering **outperformed debate** on closed-book tasks — debate pays for its overhead only where the challenger genuinely holds private information [36], with the pro-debate counterweight existing under different task structure [37]. "Adversarially verified" is therefore a claim about a conditional regime, not a property.

On the promotion ladder, the retrieved precedents that survive scrutiny share three features: objective published thresholds, re-checking at the moment of the restricted action, and a named re-grant or appeal path. Wikipedia's `autoconfirmed` group requires "at least 10 edits … and after 4 days have passed since the time of their first edit", `extended-confirmed` 500 edits and 30 days, and "the required threshold … is checked every time a user attempts to perform a restricted action", with re-grant through a named permissions-request page [38]. The failure mode to avoid is documented on the platform that most explicitly ties score to capability: Stack Overflow's reputation ladder produced voting rings, with 60-80% of algorithmically flagged accounts having reputation retrospectively reduced [39][40][41]. A scalar score that unlocks privileges is gameable; a *measured artifact outcome* — survived disputes, hidden-test pass rates, benchmark-family diversity — is much less so. Crucible's `AlloyRegistry` is already on the right side of that line in one important respect: it has no `transfer`, `approve` or `mint` reachable by anyone but the forge, ERC-5192 `locked()` returns true for minted tokens, identity epochs zero a window without erasing the lifetime book, and tier math is integer (`wins >= 10 && survived >= 1` → Steel) [42]. It cannot be bought. What it lacks is the published-version-and-appeal half of the precedent.

## 5. Execution isolation and evidence integrity [Confidence: High]

Every authoritative source retrieved treats a plain container as a *weakened boundary*, not a sandbox. Google's GKE Sandbox documentation states that multi-tenant clusters and clusters running untrusted workloads "are more exposed to security vulnerabilities than other clusters" [43]; the Kubernetes Pod Security Standards require that "Privileged Pods disable most security mechanisms and must be disallowed", that added capabilities "must be disallowed", and that "HostPath volumes must be forbidden" — with the Baseline capability list strictly looser than Crucible's `--cap-drop=ALL` [44]. Practitioner writing states the decision rule directly: "Standard Kubernetes containers share the host kernel. For untrusted code execution, this is not sufficient. You need Kata Containers or gVisor" [45], and for adversarial tenants specifically, "Kata Containers or Firecracker provide stronger security" [46][47]. **One negative result worth recording:** the widely-quoted "containers do not provide a secure sandbox" sentence is *not* on the Kubernetes Pod Security Standards page; that attribution has rotted and must not be repeated [44].

The middle rung has a caveat that matters more for an evaluation platform than for a web service. gVisor documents its own limits: it is "not a VM", "not a syscall filter … nor a wrapper over Linux isolation primitives", and it "does not presently implement every system call, `/proc` file, or `/sys` file so some incompatibilities may occur", with a penalty on syscall-heavy workloads [48]. For Crucible that is not merely a performance question — an adversarial agent can fail *closed* into an inconclusive run, and an inconclusive run in this product is an economic outcome, not a log line. Stronger isolation buys safety by subtracting compatibility, and the harness must be able to tell "blocked" from "failed".

The shared-host dimension is the one this deployment actually lives in. GitHub's own Actions security reference concedes that self-hosted runners "do not have guarantees around running in ephemeral clean virtual machines, and can be persistently compromised by untrusted code in a workflow", and recommends them only for private repositories because "forks of your public repository can potentially run dangerous code" [49][50]; live exploitation of exactly that path for persistence is documented [51]. Every CI job in this repository runs on `[self-hosted, linux, X64, crucible]`, and the mitigation in place is a fork-guard condition on all seven jobs — which is the right control, and is also why the guard's absence would be invisible to the suite.

Attestation is where the repo is thinnest, and the standard exists to be met. SLSA's levels are "a series of levels that provide increasing supply chain security guarantees", provenance "describes what entity built the artifact, what process they used, and what the inputs were", L1 is "trivial to bypass or forge", and L3 requires a hardened build platform that prevents runs from influencing each other [52]. Crucible today generates **no SBOM, no provenance and no signature** for anything (grep across `.github/` finds none), while `dependabot.yml` covers `npm` and `github-actions` but not `docker`, and the images float: `foundry-rs/foundry:latest`, `node:22-alpine`, `caddy:2-alpine`. The honest ceiling deserves stating as loudly as the gap: attestation proves *which* software stack ran, never that the judge decided correctly — and even hardware enclaves, the strongest available claim, are "known to be vulnerable to a powerful class of controlled-channel attacks" in which an untrusted OS can recover secrets "without resorting to page faults" [53]. An "attested runner" sentence must therefore name what is attested and what is not.

The upload and grader-tamper surfaces have published, citable requirements that map onto this product's inputs almost line by line. The grader-separation pattern is documented by the reference harness for agentic software evaluation: binary test assets are staged into the container only at evaluation time because "test data in the image would be visible to anything with a shell in it", with the model patch applied before test execution and grading as separate stages [54][55]. Sponsors' archives hit CWE-409 (data amplification: DoS by amplification, CPU and memory consumption; the referenced guidance is to limit *uncompressed* size and to extract archives safely) [56], CWE-22 path traversal, whose observed examples include Zip Slip in archive libraries [57], and a live 2026 advisory for exactly this class in a tar extractor that "did not sufficiently validate TAR archive entry paths" [58]. OWASP's upload guidance adds the operational list: application-generated filenames, size and name-length limits, don't trust `Content-Type`, store outside the webroot, scan or sandbox the content, validate *after* decoding, and "there is no silver bullet … implementing a defense in depth approach is key" [59] — while the retrieval pass found **no** Tier-1 verbatim text for the OWASP agentic threat names the brief asks the UI to enumerate, so those names must not be attributed to OWASP without a direct fetch [60][61][62].

## 6. The enterprise governance surface a reviewer will audit [Confidence: Medium]

Four independently verifiable things, and every one is a "show the measurement, not the intention" requirement.

**A service level that was measured before it was claimed.** Google's SRE Book defines an SLO as "a target value or range of values for a service level that is measured by an SLI", distinguishes an SLA as a contract that "includes consequences of meeting (or missing) the SLOs they contain", requires that "SLOs should specify how they're measured and the conditions under which they're valid", and prescribes an error budget — "a rate at which the SLOs can be missed" [63]. The repo's own `docs/enterprise` line — do not promise an SLA until measured — is therefore standard practice, and the retrieved text supports naming it as such.

**Tenant isolation that is tested, not designed.** The class is API1:2023, Broken Object Level Authorization, rated Easy/Widespread/Easy, whose prevention list ends with the sentence a reviewer will quote back: "Write tests to evaluate the vulnerability of the authorization mechanism. Do not deploy changes that make the tests fail" [64]. ASVS V4.2.1 requires verification that "sensitive data and APIs are protected against Insecure Direct Object Reference (IDOR) attacks targeting creation, reading, updating and deletion of records", V4.1.1 that enforcement happens "on a trusted service layer", and V4.1.3 least privilege [65]; the testing method is published for automation of the authorization matrix, for rendering it as audit evidence, and for CI-gated horizontal/vertical/**tenant-isolation** regression [66][67][68], with a dedicated multi-tenant cheat sheet whose section list includes "Verify Tenant Isolation" and cache/session isolation [69]. Crucible today has none of this because it has no tenants — which is the finding, not the absence of a feature.

**An audit trail that is defensible rather than exported.** The design precedent is Certificate Transparency: Merkle "consistency proofs prove the append-only property of the tree", and audit paths let "anyone audit the certificate logs themselves" [70]; RFC 3161 supplies the primitive for asserting "that a datum existed before a particular time" [71]; NIST SP 800-92 states log management "also involves protecting the confidentiality, integrity, and availability of logs", down to digest-based transport integrity [72]. The nearest thing Crucible has to this is `VerificationReceipt`, an on-chain soulbound ERC-721 whose minting is off unless the owner wires it, and whose address is unset in `.env.example` — so the public `/.well-known/crucible.json` says `verificationReceipt: null`. The append-only half of the story is real on-chain and absent off-chain: the indexer has a monotonic cursor with a quiet-tail proof and reorg-aware rebuild [73], but there is no log the reviewer can independently verify.

**Process artifacts tied to named standards.** SBOM's floor is NTIA's seven data fields — supplier, component name, version, other unique identifiers, dependency relationship, author, timestamp — in SPDX, CycloneDX or SWID, derived from EO 14028 [74]; in the EU the Cyber Resilience Act's Annex I Part II vulnerability-handling duties are being harmonised clause-by-clause onto EN ISO/IEC 29147:2020 clauses 5, 6 and 9 and ISO/IEC 30111:2020 clause 7, with Recital 77 noting manufacturers "should not be obliged to make the SBOM public", reporting duties from 11 September 2026 and main obligations from 11 December 2027 [75][76]. Vulnerability disclosure content is pinned by a free government text: SP 800-216 cites ISO/IEC 29147 Section 9 for disclosure policies, 6.2.1/6.2.2 for the reporting mechanism and Section 7 for the advisory mechanism [77][78]. For AI specifically, NIST AI 600-1 contains MEASURE 2.7 ("AI system security and resilience … are evaluated and documented"), MEASURE 1.3 on independent assessors, and suggested actions MP-5.1-005 (adversarial role-playing, GAI red-teaming, chaos testing), MP-2.3-005 (regular adversarial testing) and MS-2.8-002 (documenting instructions given to red-teamers) [79]. The EU AI Act's Article 53(1)(a) requires keeping technical documentation "including its training and testing process and the results of its evaluation" at least to Annex XI, Article 55(a) requires model evaluation "including conducting and documenting adversarial testing", both in force from 2 August 2025, with the voluntary GPAI Code of Practice published 10 July 2025 as one route to demonstrating Article 53 compliance and non-adherents required to "demonstrate alternative adequate means of compliance" [80][81]. ISO/IEC 42001 is the AI-management-system standard — and ISO itself states it "does not certify organizations", certification being carried out by independent bodies [82], with a hyperscaler's offering page as the shape a vendor publishes when it does hold one [83].

The honest asymmetry for a solo team: certification is structurally out of reach (a paid audit by an accredited body, no free path), and the retrieved critique that these artifacts are theatre rests on a practitioner forum thread rather than a documented case [84]. **The strongest rhetorical weapon available to the skeptical reading — a named breach at a vendor that held a SOC 2 or ISO 27001 attestation at the time — could not be sourced at all** despite targeted searching; the closest candidate did not establish the attestation at the time of the incident and is recorded as insufficient [85]. §11 keeps it as an open question. What a small vendor can offer instead is exactly what this repository's most distinctive pages already do: published methodology, machine-readable claims with provenance, and a page that lists the promises it does *not* keep.

## 7. Money UX: what a signer is told, and what an auditor needs kept [Confidence: High]

Crypto-native guidance and enterprise-audit guidance optimise different events, and the divergence is a finding rather than a nuisance.

The 2026 crypto-native position is that readability *at the signing moment* is the fix, and it is now a standard: the Ethereum Foundation announced Clear Signing on 12 May 2026 under ERC-7730 and ERC-8176, with Ledger transferring stewardship to EF's Trillion Dollar Security initiative, framed as "What You See Is What You Sign", explicitly because blind signing "contributed to billions in user losses, including the Bybit hack" [86][87]. The lineage runs through ERC-6384 (2023), whose premise is that "a user's wallet needs to be able to display a human-readable interpretation of what a given signature will do on-chain" [88]; EIP-712 makes a readable prompt *possible*, not mandatory or truthful [89]. **A correction to the brief that prompted this section: there is no live EIP-5777 governing human-readable signatures**; the real chain is 6384 → 7730/8176, and citing the former would have been a fabricated standard.

The peer-reviewed dissent is that readability is not comprehension. Two formative studies of how users interpret *authentic* signing requests identify an explicit "usability-security gap" — users misinterpret structured EIP-712 payloads [90]; the sample sizes and error rates were not retrievable in budget, so the finding is cited qualitatively. Ledger's blind-signing *statistics* likewise did not appear in the retrieved text and are not used [87][91].

Enterprise-audit guidance asks for the retained record instead: fee basis, fee version, rounding direction, payer and receiver, gross versus net, worst-case loss, refundability, lockup, dispute stakes — all reconstructable after the fact, by whoever is audited, not merely legible once at the prompt. A screen can satisfy EF and fail an auditor, because "I saw it" is not evidence that "I was told the right thing in the version that settled". This is where the repo's own rules are ahead of the industry: `AGENTS.md` requires `5% · 500 bps` rather than bare bps, unknown rendered `—` rather than `0`, minimums rounded up and payouts truncated, and money that never crosses a float ([apps/web/src/lib/eth.ts:27-46](file:///C:/Users/HP/Desktop/crucible/apps/web/src/lib/eth.ts#L27) parses digits via `BigInt` and refuses sub-wei input rather than truncating silently). Those are audit-side controls, not wallet-UX controls — and the live audit showed them violated on the landing page while honoured on `/clock`.

Two concrete UX consequences follow, both now implemented. First, the demonstration warning must sit **at the signature**, not at the login: `/sign-in` carried the "test ETH worth nothing" sentence while `/trials/new` and `/forge` — the two screens that open a wallet prompt — carried neither it nor the word for the transaction cost anywhere on the site. The notice now appears at both, and states that this page does not measure the network fee because it does not ask the node, pointing at the wallet's own figure as the one to read [92]. Second, no fee **version** is displayed anywhere on the live site, so the record cannot be tied to the schedule that actually settled — which is ADR-0019's requirement, not merely a preference [93].

On pricing, the retrieval found almost nothing usable and that is itself the finding: the only concrete figure surfaced was a competitor's own comparison page stating a $249/month floor with no per-seat charge [94] — the weakest possible source type for a money claim. No pricing was retrieved for Patronus, Galileo, Scale, Langfuse, HumanLayer or Terminal-Bench, so "leaderboards are free and enterprises pay per outcome" remains an untested assumption here, and the 5%-of-payout-versus-subscription question is unanswerable from this evidence.

## 8. The live deployment as evidence [Confidence: High]

The audit was read-only, no wallet connected, nothing signed, and screens behind the signature gate are explicitly not described.

What holds up, and should be defended as the product's actual differentiator: `/clock`, `/assay`, `/claims` and `/escrow` are the strongest trust surfaces in the product. Every number carries its Solidity provenance; the em-dash policy is stated *in the interface* ("An em dash means the number was not measured — never that it was zero"); `/assay` publishes its own dead-letter queue and trip-wires; `/claims` lists the promises it does not keep, though its summary line ("13 of 19 … 3 are not enforced yet") silently omits the 3 "Partly" rows; `/escrow` answers "where is my ETH" with no wallet, no signature and the correct pull-ledger explanation. ## 9. The economics question, settled as an option analysis [Confidence: High]

Because both briefs put a fee number in their first pages and `AGENTS.md` puts a new-ADR requirement on any change to one, this was scoped as a four-option decision and written up as [ADR-0019](file:///C:/Users/HP/Desktop/crucible/docs/adr/0019-both-fee-schedules-legible.md).

The two rates differ in four dimensions, not one: **rate** (500 vs 1500 bps), **payer** (the agent's payout vs the sponsor's posting), **timing** (deducted at settlement vs collected at `postTrial` with `msg.value != reward + fee` reverting), and **refundability** (the legacy fee is simply not charged when a break lands; the Arena fee is refunded alongside the reward on O3/O6/O7/O8 and reaches the treasury only on O1/O2) [95]. Option A, adopt 15% platform-wide, re-prices the legacy escrow, moves the charge between parties, and would take a fee on rows where the Arena today refunds it — that is ADR-0001's pivot, and it is the third time this number has arrived from an external document. Option B, adopt 5%, discards ADR-0014's pricing of the challenge bond to the cost of verification: the Arena's rate funds a docket, a seat pool and a committee the legacy law does not have. Option C, keep both silent, *is* the current state and is the failure mode. Option D, keep both and label both, costs a read-model change and one page, moves no constant, and is fully reversible.

The decision adopted is D, with the mechanism spelled out: `economics.feeBps` becomes a list with one entry per wired protocol, each carrying its address and provenance, so the UI cannot invent the Arena rate and cannot hide it either; and the Arena gets a read surface before anyone argues about its fee again. One documentation trap was recorded on the way: the label `floor_remainder_to_treasury` in `params/crucible.params.json:39` is true of the seat pools ([Arena.sol:987](file:///C:/Users/HP/Desktop/crucible/crucible-contracts/contracts/Arena.sol#L987)) and **not** of the fee, and must not be presented as a fee rule.

## Methodology

Depth **deep**; standard's default was overridden by the requester's answer. Nine subagents across two retrieval waves plus a verification pass, all dispatched in parallel where independent: four external Retrieval agents (areas 1-2, 3, 4, 5-6), two repository ground-truth agents (contracts/economics; platform/security/deploy/docs), one live-site browser audit agent, then two Gap-Fill agents aimed at the specific holes triangulation found thin (governance standards; trust tiers, COI, grader tampering, archive abuse, attestation limits), and one Verification agent for citation spot-checks.

Merge protocol applied: source numbering collisions between subagents (two agents were assigned overlapping `START_INDEX` ranges; four entries collided) were resolved by renumbering into a single sequential list, deduplication by URL kept the richer extract, and tier tags were carried forward. Triangulation assigned `[High]` only where three or more independent sources agreed with at least one Tier 1 or Tier 2; `[Medium]` where two agreed or where three Tier-3 sources supported a claim (the cap was applied to §6 for exactly that reason). Recency was tiered: leaderboard and framework evidence <18 months; arXiv/standard bodies and the SRE Book allowed at any age and marked foundational; blog-sourced magnitudes kept their age visible.

Outline refinement (Phase 3.5) was under the 50% limit: §8 (the live deployment) was added because the browser audit produced well-evidenced findings that the planned sections could not hold, and §1 (repo ground truth) was promoted to the front because both briefs' premises turned out to be wrong in ways that changed downstream recommendations. §9 exists because the requester chose "evaluate both as an ADR option analysis" rather than accepting either document's fee assertion.

Quality gate: after wave 1, all six areas had ≥2 sources and the source count already exceeded the deep target, but four areas lacked a critical/opposing view or a required evidence type, so wave 2 ran as gap-fill only rather than a full second retrieval. This is why wave 2 produced 39 sources against a much narrower brief.

Citation spot-check: twelve of the highest-impact claims — the Berkeley RDI per-benchmark percentages, the [10] coefficient direction, the UMA incident's $7M/5M-token/25% figures, the panel-size curve and the four mechanism rules attributed to [26], the Clear Signing date and ERC numbers plus the non-existence of EIP-5777, the DeepMind 35%/48% figures and the direct-QA result, the SWE-bench verbatim sentence and its location, the Wikipedia thresholds and re-check sentence, the IBA non-waivable list, the SRE Book's three definitions, NTIA's seven fields, and NIST AI 600-1's measure identifiers — were sent to a Verification agent for re-fetch.
